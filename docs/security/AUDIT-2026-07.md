# Koberlet — Security Audit Report

**Target:** `dnns-es/koberlet` @ `main` (v1.4.9, commit `43e5503`)
**Scope:** full repository — Electron main/preload, `lib/*`, `renderer/*`, build & deps
**Type:** independent, good-faith return-favour audit (private, coordinated disclosure)
**Method:** cold static read + benign local reasoning + `npm audit`. No live infra was attacked; no real keys/funds used.

## 1 — Critical: Auto-update executes unverified code (RCE as the wallet)

**Location:** `main.js:487-540` (`update:check` / `update:apply`)
**Attacker & preconditions:** anyone who can control the response from `descargas.dnns.es` — a compromised/misconfigured update server, a stolen deploy credential, a CDN/DNS takeover, or a TLS-MITM position (hostile Wi-Fi, corporate proxy, a mis-issued cert). No access to the victim's machine is needed.
**Impact:** **full wallet compromise.** The attacker's code runs as the Koberlet main process, which holds the decrypted vault while unlocked and can read `vault.json`, exfiltrate seeds/keys, and sign arbitrary transfers. This is the highest-impact outcome in the threat model.

**Why it happens.** `update:apply` does:

```
main.js:501  const r = await fetch(UPDATE_URL + '/latest.json', …)
main.js:503  const appUrl = j.appUrl;          // taken verbatim from the JSON
main.js:510  const res = await fetch(appUrl, …) // fetched with NO host allowlist
main.js:513  fs.writeFileSync(zipPath, Buffer.from(await res.arrayBuffer()))
main.js:515  spawn('powershell', … Expand-Archive … )   // extract
main.js:527-528  move resources/app -> app_old ; move upd/app -> resources/app
main.js:530  start "" exe                       // relaunch from the swapped-in code
```

The comment on `main.js:482` documents a `latest.json` shape of `{version,url,sha256,notes}` — but **`sha256` is never read, and nothing is ever hashed or signature-checked** (confirmed: no `createHash`/`digest`/`verify`/`publicKey` anywhere in `main.js`). TLS is the *only* integrity control, and `appUrl` is not even constrained to the `descargas.dnns.es` origin — a malicious `latest.json` can point the download at any host. Combined with `updateMode:'auto'` (`renderer/app.js:105-108`), a tampered `latest.json` yields code execution on next launch **with no user interaction**.

**Remediation (in priority order):**
1. **Sign the update and verify before executing.** Ship an embedded Ed25519 (or minisign/cosign) *public* key in the app; have `latest.json` carry a detached signature over the zip (or over a manifest containing its SHA-256). After download, recompute the digest, verify the signature against the pinned public key, and **refuse to extract/swap** on any mismatch. This is the real fix — a hash alone from the same channel is not integrity (attacker controls both).
2. If a signing pipeline is not yet available, as an interim: (a) verify the advertised `sha256` against the downloaded bytes, and (b) hard-pin `appUrl`'s origin to `https://descargas.dnns.es/…` and reject anything else. (Interim only — does not stop a server compromise.)
3. Consider TLS certificate/public-key pinning for the update host.
4. Code-sign the shipped executable (see #9) so the OS also gates tampering.

## 2 — High: Outdated Electron runtime (17 known advisories)

**Location:** `package.json:22` (`"electron": "^31.3.1"`), lockfile pins **31.7.7**. The portable build copies `node_modules/electron/dist` (`build-portable.sh:20`), so Electron is the **runtime engine**, not just a dev tool.
**Impact:** Electron ≤ 39.8.4 carries 17 advisories flagged by `npm audit`, including **ASAR Integrity Bypass via resource modification** (GHSA-vmqv-hx8q-j7mg) — directly relevant to #1's `resources/app` swap — plus several renderer use-after-free / IPC-spoofing / origin-confusion issues. On a wallet, any renderer→main escape is a path to the keys.
**Remediation:** upgrade to a current supported Electron major and re-test. Track Electron security releases; wallets should not lag majors. Re-run `npm audit` after the bump.

## 3 — Medium: XSS from the third-party indexer into `innerHTML`

**Location:** data enters at `main.js:437-455` (`fetchAccountTxs`, plain `fetch` of `https://kdaindex.dnns.es/txs/account/…`), is forwarded unescaped through `history:list` (`main.js:462-467`) as `amt` (`t.amount`), `tok` (`tokLabel(t.token)` — `String(t).split('.').pop()`, no escaping), `chain` (`t.chain`), and rendered via `innerHTML` at `renderer/app.js:427-434`.
**Attacker & preconditions:** whoever controls the indexer response — a compromised `kdaindex.dnns.es`, or a TLS-MITM of that fetch. The malicious fields ride in a transaction record for an account the victim views in History.
**Impact — bounded by the CSP, but real.** The CSP (`renderer/index.html:5`) is `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; connect-src 'self';`. Because `script-src` falls back to `'self'`, injected inline `<script>` and event-handler attributes (`onerror=`…) **do not execute**, and `connect-src 'self'` + `img-src 'self' data:` block remote exfiltration. So this is **not** direct code execution. It **is** HTML/CSS injection into the wallet UI: an attacker can render convincing fake content, overlay a spoofed "send to this address" prompt, or reposition/obscure elements (clickjacking-style) to trick the user during a real operation — a meaningful phishing primitive in a funds-moving app. `t.amount`/`t.chain` are also injected without type-coercion.
**Remediation:** stop using `innerHTML` for indexer-derived data. Build these rows with `textContent`/`createElement`, or HTML-escape every interpolated field. Coerce `amt`/`chain` to `Number`. Treat *all* remote-sourced strings (indexer, and by extension any label/symbol/address) as untrusted at the DOM boundary. Tighten the CSP further if feasible.

## 4 — Medium: `config:set` accepts arbitrary renderer config (repoint signing endpoints)

**Location:** `main.js:480` (`config:set` writes whatever the renderer sends, unvalidated) → the stored `node`/`rpc` values are later used to broadcast signed txs in `send:kda` (`main.js:357-359`), `send:evm` (`main.js:368-371`), swap and bridge.
**Attacker & preconditions:** any code running in the renderer — e.g. chained from #3, or a future injection. `config:set` has no schema/allowlist and no unlock check.
**Impact:** an attacker who can call `config:set` (or influence stored config) can repoint the Ethereum RPC / Kadena node to a hostile server. That server can eclipse the client (feed fake balances/quotes to induce bad sends), and observe transaction metadata. Signed material still requires the key, so this is misdirection/eclipse rather than direct theft — but it degrades the integrity of what the user sees vs. signs.
**Remediation:** validate `config:set` against a strict schema; constrain endpoints to an allowlist (or clearly mark custom RPCs and warn). Don't let the renderer freely overwrite security-relevant fields; keep signing endpoints in main-process-owned config.

## 5 — Medium: Unvalidated recipient interpolated into Pact code

**Location:** `lib/kda.js:56` — `code: \`(coin.transfer "${from}" "${to}" ${amt.toFixed(12)})\`` with `to` never validated (confirmed: no regex/validation of `to` in `kda.js` or in the `send:kda` handler `main.js:353-360`). Same pattern for `account` in `lib/swap.js:77` and recipients built in `lib/bridge.js`.
**Attacker & preconditions:** a hostile counterparty / phishing flow that supplies a crafted `to` string, or any path that sets the recipient without the user reading it. A `to` containing a `"` breaks out of the Pact string literal.
**Impact:** two concerns. (a) **String injection** into the executed Pact code — a malformed/crafted recipient changes the code that is hashed and signed. (b) More importantly this is a **blind-signing surface**: the app signs exactly the interpolated `code`, and the only thing standing between the user and a malicious transfer is the confirmation modal text. The KDA send does not enforce that `to` is a well-formed principal (`k:`/`w:`/etc.) before it's baked into the signed code.
**Remediation:** validate and normalize recipients before interpolation — enforce the expected account shape (e.g. `k:<64 hex>` / valid principal), reject characters that can escape a Pact string literal, and prefer passing the recipient as `env-data` + `read-string`/`read-keyset` rather than string-concatenating into `code`. (`lib/bridge.js:16-27` already does careful recipient validation — mirror that rigor in `kda.js`/`swap.js`.)

## 6 — Low: Non-constant-time passphrase comparison

**Location:** `main.js:308,355,365,399,424` — `if (passphrase !== unlocked.pass)`.
**Impact:** `!==` on the in-memory passphrase is not constant-time. Practically low risk (local, in-memory, no remote timing oracle, and the value-moving paths also need the key), but it's a cheap defense-in-depth fix.
**Remediation:** compare with `crypto.timingSafeEqual` over equal-length buffers (or compare a stored hash of the passphrase). Better: gate re-auth on re-deriving the vault key rather than holding/comparing the plaintext passphrase in memory at all.

## 7 — Low: Vault KDF parameters read from file with no floor

**Location:** `lib/vault.js:39` — `abrir()` uses `raw.kdf.N/r/p` straight from `vault.json` with no minimum.
**Impact:** the write path pins strong params (`N=2^15`, `lib/vault.js:7`), but the read path trusts whatever the file says. An attacker who can rewrite a victim's `vault.json` could set `N=1`; if the app later re-saves under those params, the vault becomes cheap to brute-force offline. Bounded (needs local file write, and GCM auth still requires the right key to open), hence Low.
**Remediation:** enforce minimum KDF parameters on read (reject or upgrade anything below policy), and always re-encrypt with current strong params on save. Consider authenticating the KDF params (they're already covered by GCM only for the ciphertext, not the header).

## 8 — Low: `clist` capability amount can differ from executed `code` amount

**Location:** `lib/kda.js:50-56` — the signed `coin.TRANSFER` capability uses `{ decimal: String(amt) }` (`:52`) while the executed code uses `amt.toFixed(12)` (`:56`).
**Impact:** for values that stringify to scientific notation or differ in precision (e.g. `1e-7` → clist `"1e-7"` vs code `"0.000000100000"`; `1.5` → `"1.5"` vs `"1.500000000000"`), the capability argument and the code argument are textually different. At best the node rejects the tx (managed-cap mismatch → failed sends / poor UX); at worst it invites confusion about exactly what was authorized. Not a fund-theft vector on its own, but a correctness/consistency defect on the signing path.
**Remediation:** compute one canonical decimal string and use it for **both** the `code` and the `clist` arg. Normalize amounts (avoid `String(Number)` scientific notation) before building either.

## 9 — Info: Unsigned build / no code signing

**Location:** `package.json:38-46` (win target `dir`), `build-portable.sh`, `build-app-zip.sh` — no `signtool`/`certificateFile`/`cscLink`.
**Impact:** the shipped executable is unsigned, so the OS offers no tamper/authenticity gate, and users get SmartScreen friction. Compounds #1 (nothing outside the app verifies the code that runs).
**Remediation:** code-sign the released artifact; ideally sign both the installer/portable and the auto-update payload, and verify the signature in the updater (#1).

## What's done well (genuine strengths)

- **Sound Electron trust boundary:** `contextIsolation: true` + `nodeIntegration: false` (`main.js:155`) with a **narrow, explicit** `contextBridge` surface (`preload.js`) — the renderer never receives raw keys. This is the right architecture and is often gotten wrong.
- **Real re-authentication on sensitive actions:** every value-moving / secret-exporting handler re-requires the passphrase (`wallet:export`, `send:kda`, `send:evm`, `bridge:send`, `swap:exec`), and secret-touching handlers check `unlocked` first.
- **Vault crypto fundamentals are correct:** AES-256-GCM with a **random 16-byte salt and random 12-byte IV per write**, auth-tag set/verified, scrypt at a sensible cost, key zeroized after use (`key.fill(0)`), and `vault.json` written `mode 0o600` (`lib/vault.js`).
- **`open:external` is constrained to `https://`** (`main.js:495`) — avoids `file:`/custom-scheme abuse.
- **Reasonable CSP** with `connect-src 'self'` and no `script-src 'unsafe-inline'`, which is exactly what bounded finding #3 from becoming code execution.
- **Careful bridge recipient handling** (`lib/bridge.js:8-27`) with explicit format validation and documented rationale — good model to extend to the other signing paths.
- **Secrets are kept out of the local history/log files**, and `.gitignore` correctly excludes vault/keys/backups.
- **Good UX safety rails:** seed shown once with a paper-backup warning, double-confirm wallet deletion, dry-run before real bridge sends.
